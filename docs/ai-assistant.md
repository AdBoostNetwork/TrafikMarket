# AI Assistant Container

Контейнер `ai-assistant` — разговорный ИИ-помощник TraffMarket: отвечает на вопросы о рынке
и объявлениях, анализирует данные пользователя, даёт советы, выполняет действия по запросу
и пишет пользователю сам по событиям. Это отдельный контейнер по образцу `app` (долгоживущий
HTTP-сервис) и `updater-scheduler` (фоновые задачи по расписанию).

Документ — контракт разработки: архитектура, границы, конвенции, шаблон инструмента, порядок
работ. Полный каталог возможностей помощника — в [docs/AI TOOLS.md](AI%20TOOLS.md).

---

## 1. Назначение и модель работы

Помощник построен на **LLM с tool-calling**. LLM (через OpenRouter) — «мозг», который понимает
вопрос и решает, какие инструменты вызвать. **Инструмент** — написанный нами код, достающий
реальные данные из БД платформы или выполняющий действие. Модель никогда не обращается к данным
напрямую и ничего не выдумывает: она только выбирает инструмент и пересказывает результат.

Цикл ответа на вопрос:

1. Пользователь задаёт вопрос → `app` передаёт его в `ai-assistant` вместе с `user_id`.
2. LLM анализирует вопрос и возвращает список инструментов, которые нужно вызвать.
3. Наш код исполняет инструменты (SQL к БД платформы / HTTP к `app`) и возвращает данные модели.
4. LLM собирает из данных ответ на человеческом языке; ответ стримится пользователю.

Три контура работы:

- **Аналитика** — чтение данных платформы (read-only SQL). Большинство инструментов.
- **Действия** — изменение данных платформы строго через HTTP-ручки контейнера `app`.
- **Проактив** — фоновые проверки триггеров по расписанию, уведомления через существующую
  Push-систему платформы.

## 2. Границы

- `ai-assistant` **не пишет в основную БД напрямую**. Любое изменение данных платформы — через
  HTTP-ручки `app`, где живёт бизнес-логика и валидация. Причина: единственный источник правды
  для записи — `app`; дублирование логики в помощнике неизбежно разойдётся с ней.
- Аналитические инструменты читают основную БД **под отдельным read-only пользователем PostgreSQL**.
  Помощник физически не может изменить данные платформы SQL-запросом.
- `user_id` приходит от `app` из авторизованной сессии и передаётся инструментам нашим кодом.
  Модель `user_id` во входных параметрах инструментов не получает — иначе prompt-injection
  позволил бы запросить чужие данные.
- Пакет `backend/app_backend/` (старый бэкенд) — только read-reference по доменной логике,
  не трогать и не импортировать.
- external_data (TGStat, MAX Dashboard) в этом контейнере не используется — помощник читает
  уже сохранённые в БД данные объявлений.

## 3. Архитектура и связи

| Откуда | Куда | Протокол | Назначение |
|---|---|---|---|
| `frontend` / `main-bot` | `app` | HTTP | Пользовательский запрос к помощнику (через `app`) |
| `app` | `ai-assistant` | HTTP (Docker network) | Проксирование запроса + `user_id`, стрим ответа |
| `ai-assistant` | `postgres` (основная БД) | SQL (read-only role) | Аналитика: чтение объявлений, цен, сделок |
| `ai-assistant` | `postgres` (БД помощника) | SQL | История диалогов, память, подписки, снапшоты |
| `ai-assistant` | `app` | HTTP (Docker network) | Действия: создание/редактирование объявлений и т.д. |
| `ai-assistant` | OpenRouter | HTTPS | Вызовы LLM |
| `ai-assistant` | Web Search API | HTTPS | Инструмент «Поиск во внешних источниках» |
| `ai-assistant` (проактив) | Push-система платформы | HTTP/через `app` | Доставка уведомлений |

**Изоляция БД.** Помощник использует **отдельную базу данных** в существующем контейнере
`postgres` (не схему в основной БД, не отдельный контейнер). У неё собственный набор
Alembic-миграций, отдельный от корневого `alembic/`. Основную БД помощник видит только через
read-only роль.

## 4. Структура пакета

Пакет `backend/ai_assistant/` следует конвенциям `backend/app/` (слои router → service →
repository, иерархия ошибок, логгер). AI-специфичные части добавлены поверх.

```text
backend/ai_assistant/
  main.py                    # точка входа сервиса: AI_HOST, AI_PORT → uvicorn (как app/main.py)
  app.py                     # FastAPI инстанс, lifespan, подключение роутеров
  logger.py                  # get_logger(name)
  core/
    config.py                # чтение env
    errors.py                # иерархия ошибок (по образцу app/core/errors.py)
  api/
    routers/
      chat.py                # POST /chat — приём (user_id, message), SSE-стрим ответа
    schemas/
      chat.py                # request/response Pydantic-модели
  llm/
    client.py                # клиент OpenRouter (OpenAI-compatible), провайдер-независимый слой
  agent/
    loop.py                  # цикл tool-calling: LLM → вызовы инструментов → сборка ответа
    registry.py              # реестр инструментов (регистрация декоратором)
    context.py               # ToolContext: user_id, сессии, http-клиент app
  tools/
    base.py                  # ToolSpec, базовый класс Tool
    analytics/               # аналитические инструменты (read-only SQL), один модуль = один инструмент
    actions/                 # инструменты-действия (HTTP к app)
    external/                # веб-поиск
  prompts/
    system.md                # системный промпт и персона
    <fragment>.md            # промпт-фрагменты (правила подачи, поведение при незнании)
  appclient/
    client.py                # HTTP-клиент к контейнеру app для действий
  db/
    main_session.py          # read-only session factory к основной БД (аналитика)
    ai_session.py            # session factory к БД помощника (память, снапшоты)
    dependencies.py          # init/get для обеих фабрик
  memory/
    repository.py            # история диалогов, память пользователя, подписки
  snapshots/
    runner.py                # фоновый сбор снапшотов цен и метрик (по образцу updater/scheduler)
  proactive/
    runner.py                # фоновые проверки триггеров, отправка уведомлений
  ai_alembic/                # миграции БД помощника (отдельно от корневого alembic/)
```

Промпты хранятся в `prompts/` текстовыми файлами, а не строками в коде — чтобы правки тона
не требовали изменения Python-модулей.

## 6. Контракт инструмента

Один инструмент = один модуль с тремя частями: **спецификация** (для модели), **исполнитель**
(наш проверенный код), **тест** (запуск на реальной dev-БД).

```python
# tools/base.py
from dataclasses import dataclass

@dataclass(frozen=True)
class ToolSpec:
    name: str            # уникальное имя, snake_case, напр. "get_avg_cpm"
    description: str     # для модели: что делает и когда вызывать
    parameters: dict     # JSON-schema параметров (без user_id)

class Tool:
    spec: ToolSpec
    async def execute(self, ctx: "ToolContext", **params) -> dict:
        ...
```

Инварианты:

- `user_id` **не входит** в `spec.parameters`. Исполнитель берёт его из `ctx.user_id`, который
  проставлен из авторизованной сессии `app`.
- Аналитический инструмент получает read-only сессию основной БД из `ctx`, пишет SQL через
  `sqlalchemy.text()` в стиле `backend/app/repositories/`.
- Инструмент-действие вызывает ручку `app` через `ctx.app_client`, не пишет в БД сам.
- `execute` возвращает `dict` с уже посчитанными данными — модель их только пересказывает,
  повторных вычислений не делает.
- Регистрация в реестре — декоратором `@register` из `agent/registry.py`.

Каждый инструмент из [docs/AI TOOLS.md](AI%20TOOLS.md) реализуется по этому шаблону. Названия
в каталоге — человекочитаемые; техническое имя (`spec.name`) задаётся при реализации.

## 8. Конвенции

Совпадают с `backend/app/`:

- **Слои:** router → service → repository. Router — только маршрутизация и обработка ошибок,
  repository — только доступ к данным, service — бизнес-логика.
- **Сессии:** фабрики инициализируются в `lifespan`, живут один запрос через `yield`, `NullPool`.
- **Ошибки:** иерархия от `AppError` с маппингом на HTTP-коды, наружу отдаётся код ошибки
  (`"db_error"`), не `str(e)`.
- **Логи:** `get_logger(__name__)`, формат `сообщение | ключ=значение`.
- **SQL:** `sqlalchemy.text()` с именованными параметрами, как в `backend/app/repositories/`.
- **Схемы:** Pydantic, `SuccessResponse` из общих схем для ответов-статусов.

## 9. Порядок работ (вехи)

Порядок продиктован зависимостями между частями.

1. **Каркас.** Контейнер, `core/config.py`, LLM-слой (OpenRouter), цикл tool-calling, эндпоинт
   `/chat`, реестр инструментов + 2 пилотных инструмента («Анализ объявления по артикулу»,
   «Средняя цена канала в тематике») — вертикальный срез, проверяющий всю архитектуру.
2. **БД помощника.** Миграции (диалоги, память, подписки, снапшоты), контур снапшотов.
   Запускается рано, чтобы история цен и метрик начала копиться.
3. **Аналитика по блокам.** В порядке [docs/AI TOOLS.md](AI%20TOOLS.md); базовые инструменты
   блока (несущие общие функции) — первыми.
4. **Контур общения.** Промпт и тон дорабатываются на живых инструментах — сквозной процесс,
   не разовая веха.
5. **Действия.** После появления соответствующих HTTP-ручек в `app`.
6. **Проактивный контур.** Последним — к этому времени накопятся снапшоты для триггеров.

## 10. Решения для проработки архитектором

Зафиксировано:

- LLM — OpenRouter, провайдер-независимый слой (задел под локальную Ollama).
- БД помощника — отдельная база в контейнере `postgres`, свой Alembic.
- Аналитика — read-only SQL к основной БД; действия — только HTTP к `app`.
- Транспорт — `frontend`/`bot` → `app` → `ai-assistant`, `user_id` от `app`, стрим ответов (SSE).
- Инструмент — модуль «спецификация + исполнитель + тест», регистрация декоратором,
  промпты в `prompts/`.

Требует проработки:

- Проактивный контур и контур снапшотов — второй процесс в контейнере или отдельные контейнеры
  из того же образа (по образцу `scheduler`).
- Схема БД помощника: таблицы диалогов, памяти, подписок, снапшотов цен/метрик.
- Создание read-only роли в основной БД: миграция или init-шаг.
- Формат контекста сессии, передаваемого модели (история диалога, память, лимиты).
- Провайдер веб-поиска и обвязка (фильтр источников, цитирование).
